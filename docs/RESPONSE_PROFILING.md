## 确定性对象操作的边界

Dynamic State 现有动态 schema 是描述及校验契约，还不是可执行的 Object 行为契约。应继续使用它作为事实来源，而不是新增独立背包/对象数据库来复制位置、归属或状态。

可行的最小结构是“对象引用 + 已批准的操作契约”：对象通过 `subject_id` 关联当前属性，操作声明允许的输入、必须满足的前置条件、读写权限和有限状态变更。操作只引用现有、类型明确的状态，使用有限比较及原子更新，不接受模型生成的 Python/JavaScript 或任意 eval。

例如拾取的规则可以检查：物品已声明可拾取、无持有人、角色与物品在同一可达位置、容量要求满足。全部条件由完整契约明确给出，才可以走零模型的 compare-and-set 事务。缺字段、未知对象、有争议的所有权、他人意愿或规则外的后果，仍交给智能链路；不能仅凭“捡起”两个字就绕过检查。

物品的实际持有人是一个领域属性值，不能混用 Dynamic State schema 的 `owner_id`。后者控制私有知识所有者，具有不可变约束。

这条快路径将来还需接入相同的授权、版本冲突、事件来源、Memory、检查点和回滚。必须有独立的合法操作来源，不能伪造模型行动，也不能让角色自行声称“这是确定性操作”就获得写权限。它应复用同一受控状态提交层；State Coder 负责概念理解，机械执行器只执行已批准的契约。操作成功也只是符合已定义的规则，并非证明规则完整模拟了现实。

当前不把拾取等领域行为硬编码进产品，也不在本轮未经实验就增加这套运行时。

## 空正文诊断：2026-11-10

两次第二项 Action Check 失败仍只是高优先级假设：Thinking 可能消耗900 Token上限，最终正文尚未生成。不能用旧记录的 `output_tokens=900 / token_source=reserved` 证明截断，也不能倒填缺失证据。三路延迟样本及限制见 [PARALLEL_ADMISSION_TRIAL.md](PARALLEL_ADMISSION_TRIAL.md)。

核对官方 [Thinking 说明](https://api-docs.deepseek.com/guides/thinking_mode/) 与 [Chat Completions 契约](https://api-docs.deepseek.com/api/create-chat-completion/)：Thinking 默认启用，`reasoning_effort=low` 不等于关闭。当前请求未显式发送开关时，诊断记 `thinking_mode=default`，不声称已经观测到服务端实际启用。是否出现推理由响应的 `reasoning_present` 单独记录。

现有 Provider 新增 `empty_content` 错误码及白名单元数据，保留到异常包装、`action_checked.provider_diagnostics` 和评测 `requests[].provider_diagnostics`：

- `finish_reason`：仅已知协议枚举；缺失或未知为 `unknown`。
- `reasoning_present`、`content_chars`：只有是否存在推理及正文字符数，不保存推理/正文文本。
- `prompt_tokens`、`completion_tokens`、`reasoning_tokens`：仅保留供应商明确提供的非负整数。推理Token不可由推理字符数或正文缺失反推，也不再加到已经包含它的 completion 总数上。
- `max_tokens`、`thinking_mode`、`reasoning_effort`：此次请求实际发送的限制/选项；未发送的值不伪造。另记录耗时与尝试次数。

失败评测优先使用响应报告的用量，包括真实的0；每个缺失输入量仍估计、缺失输出量仍保守预留，分别标记来源。Ollama 原生空响应使用其 `prompt_eval_count / eval_count / done_reason / message.thinking`，不假造单独推理Token。评测包装器关闭 Provider 内部重试，因此每条 trace 是物理尝试；普通 Provider 若内部重试，异常上的响应用量只属于最后一次失败响应，不是全部尝试的账单。

诊断只允许计数、布尔值和枚举，不持久化任意供应商字段、API Key、提示词或推理文本。失败继续拒绝接纳候选，现有重试次数与 Thinking 配置不变，没有自动提高预算、切换模型、降级接受或新增模型调用。

离线回归通过576项，包含模拟HTTP响应到 Provider、预算统计、Checker错误事件的完整模块链路，以及缺失用量、0用量、非法字段与本地接口的反例。本轮无付费请求，未证明两次历史失败的根因，也未证明关闭Thinking的语义质量。下一次授权请求若同时出现 `length`、推理存在、实际completion接近上限，才能显著加强预算耗尽判断；之后应使用固定复杂案例单独对照有效输出率、检查正确率和延迟，不先修改生产默认值。

## 测量与判断

- 每次物理请求记录模块、开始偏移、耗时、输入/输出 Token、成功/失败及用量来源。只保留摘要与哈希，不保留原始提示词或响应。
- 供应商报告的 0 Token 仍是 0，不错误替换成估算；失败响应的有效用量也保留。只有缺失用量才估计或保守预留并明确标记，不能称为已知实际消耗。
- 分别给出费用排序、耗时排序、每模块平均值和 p95。小样本 p95 仅供描述，不能视为稳定分位数。
- 请求耗时之和不是墙钟时间或并行关键路径。使用请求区间并集估算模型占用时间，剩余时间包括本地处理、调度和重试等待，不能全部叫 Python 计算时间。
- 合并审计的 State Coder 不拆出虚假的独立调用成本；独立编码与修复请求分别分类。
- 先看本次是否完成、在哪里失败、请求与重试次数，再看单位行动/完成任务的成本。未完成样本不得与成功样本直接比较。
- 定位后只选一个改动，再用相同案例、同一模型/参数/预算重复实验，同时检查完成度和信息边界退化。没有受控前后对照，不承诺降本比例。
