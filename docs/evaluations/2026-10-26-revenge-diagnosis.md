时间：2026-10-26 22:26，北京时间。只做源码核对与离线复现，零新增模型调用；本轮不修改执行策略。

## 已确认的缺陷

1. **终局需求被套入固定开场阶段。** `plan_compiler._build_simulation_blueprint()` 对所有 roleplay 固定生成 Story Setup / Conflict Evolution / Resolution，初始阶段索引为 0。没有采用模型的 `simulation_design.phase_logic` 来决定初始阶段。即使需求明确只写最后对峙，第一阶段目标仍是 Establish world state, motivations, and tensions。Scene Contract 缺失时又优先采用阶段目标而非任务目标，并默认 micro 粒度。这是明确的意图冲突，但旧真实记录没有保存当时的完整 Scene Contract，不能断言实际路由必然用了默认 micro。

2. **显式时间、地点在计划规范化时丢失。** 提取提示词的 environment 示例没有这两个字段；更直接的是 `_normalize_extracted()` 重建 environment 时不保留它们。后续 `_environment_time_context()` / `_environment_spatial_context()` 虽支持读取，但收到的已经是缺字段的对象。离线让假编译模型返回 Midnight / Throne hall，最终 Workflow 的两个字段仍为两个空字符串。这能解释空坐标风险，不代表场景正文也被删除，更不能为检查器把“父亲/父王”当作冲突辩护。

3. **共享场景的公开参与者名单不完整。** `engine` 在没有实体间连线时采用 shared_scene，其他角色的公开行动可见；构造 `known_participants` 却只收自己或具有实体连线的角色。自动编译工作流的边连接 director、actor、summary，没有实体间边。离线两角色场景中，agent_1 的名单只有 agent_1。这使角色缺少对其他独立行动者的明确认识，但不是越权漏判的唯一原因：检查器本身另有全部实体定义。

4. **同一信息重复进入模型上下文。** 连续运行已经用 `action_instruction()` 把 CONTEXT 和 ROLE 序列化成 prompt，通用 `nodes.execute_node()` 又追加 Entity definition、Simulation State、Memory、Background 等。检查器还同时接收独立状态/事件依据和包含这些材料的 actor.input。导演审计的 ACTUAL NODE OUTPUTS 与 State Coder 的 UNCODED ACTIONS 再次包含当前行动。离线一个短角色提示词为 6671 字符，角色描述出现两次；审计中同一个行动标记出现两次。这些数字属于可控复现，不是对真实运行逐请求费用的测量。

5. **停止和任务完成仍被混用。** 审计提示词允许在目标完成或继续无意义时 stop；`evaluate_run()` 只凭最后一个 stop 判断 director_confirmed_completion。引擎到达行动/轮数上限，即使 Director 最后是 continue，也仍标记 succeeded。离线分别复现了“明确未完成但 stop 被计为完成”和“Director continue、上限结束却 succeeded”。真实本轮是费用异常导致 failed，并非这一状态问题直接造成其停止。

## 语义漏判，不应伪装成确定性代码结论

- 角色系统提示词和每轮行动提示词已明确禁止代写其他角色，不是简单漏写一条规则。
- 真实已接受行动仍包含 agent_2 的台词/反应，以及 agent_1 未说出的内心内容。检查器只有 JSON、类别、引用存在性等格式约束，是否越权仍依赖模型整体语义判断；本次确实漏判。解析合法和引用存在不证明行动合法。
- 仅四条已接受行动，无决断结局。不能据此推断模型永远不会收束，也不能证明 Director 当时正确或错误地判定了停滞，因为其第一轮完整审计内容未保留在简洁结果中。

## 为什么第 19 次没发出去

累计实际 18 请求，65759 input + 7673 output tokens，按测试假设估算 $0.096451。剩余估算额度 $0.003549；单次输出上限 1600 tokens，仅输出预留按 $4/M 就需要 $0.0064，尚未加本次输入。因此下一次审计在发送前被预算预检阻止，符合保护逻辑，不是余额不足或外部 API 报错。

旧 Eval 用临时内存 SQLite，结束时销毁；最新 Markdown 没有保存完整编译结果、逐调用费用和导演审计快照。因此不能精确分摊那 65759 个输入 token，也无法还原旧检查器的原始协议错误字段。后续只需保留极简诊断摘要，不应恢复多份原始日志大转储。

## 修复顺序

先修计划意图/阶段和时间空间字段传递，再统一参与者公开名单与单次上下文组装；将角色所有权作为现有检查器的明确审计项，同时保留自由行动和非预设结局。最后区分任务完成、无法推进、达到限额，并给 Director 提供剩余执行额度。不要用强迫角色死亡、固定回合反转、关键词判定或扩大预算掩盖问题。
